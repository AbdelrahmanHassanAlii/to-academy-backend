# Phase 2.4 — Lectures and Registrations (plan only)

No implementation is included in Phase 2.3. Begin only after owner approval.

1. **Lectures model/validators/service.** Follow existing module layers; localized title/description/content, stable slug, thumbnail id, UTC scheduledAt, positive duration minutes, nullable private HTTPS meetingUrl, draft/published/completed/cancelled, SEO. Confirm final localized field contract against Courses before coding. Publishing requires usable content/date/duration; retain stable published URLs. Cancellation/completion removes public eligibility; no Zoom integration. Build projected public DTOs that always exclude meetingUrl, even after registration.
2. **Lectures HTTP and tests.** Public list/detail and protected admin CRUD, scheduling/status filters and pagination; soft cancellation instead of physical deletion. Reuse authentication/authorization/CSRF/error envelopes and explicit indexes. Display dates through Africa/Cairo Intl rules in future clients, store UTC. Test timezone input, private meeting URL exclusion, cancelled/completed visibility, invalid transitions/input and session protections. Past published lectures may remain public; upcoming listing adds future-date filtering.
3. **Registration contract and eligibility.** Define strict discriminated course/lecture target input (exactly one reference), name/required phone, optional normalized email/WhatsApp; no public notes/status. Add narrow service eligibility methods to Courses and Lectures rather than HTTP calls or cross-controller dependencies: published course with active category; published future lecture. Course pricing does not imply payment or ownership checks. Recheck eligibility at submission; document cross-document concurrency boundary.
4. **Registration persistence and abuse protection.** pending/confirmed/cancelled with admin-only notes; partial unique normalized phone+course and phone+lecture indexes as approved, across all statuses. Concurrent duplicate creates return generic409 without exposing PII; staff can reactivate cancelled records. Select a maintained phone parser for valid international/Egyptian normalization and test it before committing a new dependency. Public creation uses JSON, Origin/abuse protection and existing basic rate-limit infrastructure; no session authority or public CSRF dependency. Avoid creating public sessions.
5. **Admin workflow and CSV.** Protected list/detail, target/status filters, bounded pagination, PATCH status/notes; authorized CSV with UTF-8 BOM for Arabic, correct quoting and formula-injection protection. Stream/export with a bounded policy suitable for MVP; no PII logs, email delivery, automated WhatsApp or student accounts. Retain course/lecture records referenced by registrations.
6. **Contract and verification.** Extend OpenAPI only for implemented endpoints; document target lifecycle/cancellation and manual confirmation policy. Real MongoDB tests for eligibility, unique-index races, normalization, generic duplicate errors, private fields, authorization/CSRF and safe Arabic CSV. Run all prior suites, lint/types/format/build and spec checks, make local micro commits, await approval before push/next scope.

Dependencies: Phase 1 DB/session/logging/security, Phase 2.1 administrator authorization, Categories active references, Courses publication/archiving, existing OpenAPI/pagination conventions. Media remains a nullable syntax-checked reference until its own milestone. No frontend or external provider integration.

Suggested effort: Lectures1–2 focused days, registration rules/API2–3, CSV/security/integration1–2, owner review buffer1. Total roughly5–8 working days, subject to review and phone-normalization/export edge cases; not a commitment to bypass quality checks.
